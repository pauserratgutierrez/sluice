# Sluice 0.8.1 candidate against the 0.8.0 baseline

**What is compared.** The 0.8.1 candidate is branch `fix/hold-routing`, built as `sluice:0.8.1-rc`. Its changes:
- each hold watch is unindexed from where it was indexed;
- `RoutingKey` takes the first of the equally good columns;
- only a stream's current watch can cut.

The image does not include the second fix, for UPDATEs without an old tuple (see `../phase2/README.md`, "Bugs found"). With `REPLICA IDENTITY FULL`, as here, that code path never runs.

**How it was measured.** Three 10-min runs used the same mixes, limits and pinning as their baselines (`../../plans/v0.8.1.plan`). The baselines are the first 10 minutes of the steady phase of the clean 0.8.0 runs in `../phase2/raw/`. Every figure below comes from one script, which applies the same method to every run.

**Hold order.** The load test's issuer now writes membership holds `user_id=eq.U,room_id=eq.R` by default (`LOAD_HOLD_ORDER=user-first`), the order the 0.8.1 README advises. The 0.8.0 runs used `room_id` first, and 0.8.0 keys such a hold on either column at random. `LOAD_HOLD_ORDER=room-first` on 0.8.1 is the old order. With 0.8.1's deterministic routing, it is the worst case: every hold of a room is a candidate for every member's row. So:
- 0.8.0 → 0.8.1 room-first isolates the leak fix;
- room-first → user-first isolates the choice of column.

How each column is measured:
- **Live heap:** `next_gc / 2`, the heap live at the last GC with GOGC=100. The 0.8.0 runs before `veryhigh-main-r4` did not record it.
- **Reader µs per change:** the wall time of `DispatchSeconds` per change. It is mostly hold checks.

Every 0.8.1 run delivered 100% of messages, member updates and typing events.

The reader's delay behind the WAL end, at the unicorn:
- **0.8.0:** p50 0.08, p95 0.49, max 1.27 s.
- **0.8.1, user first:** p95 0.04, max 0.05 s.

That measure's resolution is the runner's half-second LSN sampling. In `v081-veryhigh-roomfirst` it read p95 0.55 s, while that run's messages arrived at p95 15 ms. When transactions are few and each takes tens of milliseconds to dispatch, the interpolation between samples overstates the delay. Commit → client latency is the reliable figure there.

## What it shows

- **The column a hold is keyed on decides the cost.** Holds written member first (user first) on 0.8.1 cut Sluice's CPU per change by:
  - 75% at very high (95 against 365–387 ms per 1,000 changes);
  - 80% at the unicorn on 2 CPUs (105 against 535 ms).

  The reader's time per change falls 20–24× (9.5–12.4 µs against 191–300). Each member's row is checked against that member's own holds only, not against every hold in the room. At the unicorn, 0.24 cores carry 2,320 changes/s and messages arrive at p95 6.4 ms; on 0.8.0 the same load took 1.24 cores at 305 ms. GC runs 2.4 times a minute instead of 23–31: hold checks allocated most of the garbage.
- **The leak fix alone** (room first, 0.8.1 against 0.8.0):
  - CPU per change in the first 10 minutes is the same (365 against 367/387 ms). 0.8.1 room-first keys every hold of a room on the room, twice 0.8.0's random half, and that offsets the watches 0.8.0 had leaked so far.
  - From minute 1 to minute 9, CPU per change grew 4% against 11–12%, and the live heap 4% against 12%.
- **Live heap is flat on 0.8.1 with user-first holds.** 72 → 73 MiB at very high, 545 → 558 MiB at the unicorn: 46 KiB per stream.

Limits of these runs:
- Ten minutes cover about two thirds of one `/token` cycle (15 min).
- That 0.8.1 holds a flat heap for hours is not yet measured. Phase 3 ends with a multi-hour run at very high.
- Whether 1 CPU now carries the unicorn's changes is not measured. Extrapolated from 0.24 cores at 2 CPUs, it would, with ample margin; memory would not fit in 512 MB (1.3 GiB of Go memory at 12,000 streams).

## Incidental

- `v081-unicorn-2cpu-userfirst` counted 7 `issuer_unavailable` errors. All of them fall in the last second of the run (21:40:53 UTC), after the load stopped: the issuer container stopped while two streams' `/token` calls were in flight, and Sluice revoked their shapes (14 log lines, 7 of which reached the runner). This is a harness artifact; the runner should stop renewing tokens before the stack stops.

  This is Sluice's documented behavior: a new token never keeps a grant made for the previous one, and `issuer_unavailable` is retryable, so the client subscribes again after `retry_after_ms`. It matters for phase 3 (items E and F). Every stream renewing its token while the issuer restarts loses its shapes and resubscribes, so a brief issuer outage turns into a burst of subscribe calls once the issuer is back.

## The final candidate (both fixes), 2026-10-09 22:05–23:18 UTC

The image is `sluice:0.8.1-rc2`, built from `fix/hold-routing` at `9d50809` (`../../plans/v0.8.1-final.plan`). Membership holds are written user first. Each run lasted 10 minutes; the idle ramp is phase 2's, unchanged.

- **DEFAULT against FULL.** With 0.8.1 and member-first holds the two cost the same: 91–108 ms of CPU per 1,000 changes. Neither run cut any shape, and Sluice's log has no revocation.
  - On 0.8.0 the DEFAULT runs had cut almost every grant (`../phase2/README.md`, "Bugs found").
  - Every run delivered 100% of messages, member updates and typing events.
  - `v081f-unicorn-1cpu-default` counted one `publish_failed:canceled`, a typing publish cancelled as the run stopped.
- **The unicorn at 1 CPU now passes.** 2,320 changes/s took 0.25 cores, and messages arrived at p95 7–10 ms. On 0.8.0, 1 CPU dispatched about 1,950 changes/s and fell further behind as it ran.
- **The unicorn in 512 MB does not fit.**
  - Go memory reached 866 MiB during arrival and RSS 510 of 512 MiB. The runner saw 11 restarts with no shutdown line in Sluice's log: kills for memory. Docker's own record was gone when this was read.
  - Some kills came only seconds after Go memory read 144–382 MiB, because thousands of clients reconnect at once after each kill.
  - Delivery was 16%. `msg_gap_after_resume` was 0: no change was lost on a stream told it had resumed.
  - The 14 `shape_not_authorized` are `hold exists on public.room_members: context canceled`: the EXISTS of a grant whose request was gone. None is a hold cut.
- **Idle ramp:** 15,000 streams in 1,359 MiB of Go memory (0.8.0: 1,394). Live heap ~44 KiB per stream on both versions; the leak needs `/token` refreshes over time to show.
- **Live heap at 12,000 streams rose 2–3 MiB a minute.** That is 545 → 572 and 543 → 564 MiB, noisy, at about 800 `/token` calls a minute, against ~15 MiB a minute on 0.8.0.
  - Ten minutes are two thirds of one token cycle, so these runs cannot tell a transition that levels off from a small retention per refresh.
  - `registry.Rebind`, called on each re-grant, unindexes and replaces the old subscription. No retention was found in the code.
  - To settle it: a run longer than two token cycles.
